# Local-only Cloudflare read/write contract foundation

**Do not deploy the default or local-write config.** This is a synthetic-data D1/Worker acceptance fixture, not a production feed migration. The application remains Vercel Next + Supabase, unchanged. `wrangler.jsonc` deliberately has a fake UUID, unique local-only name, `workers_dev: false`, `preview_urls: false`, and no route/account or real resource binding. A separately reviewed `wrangler.staging.jsonc` pins the newly created isolated staging D1, but does not authorize a Worker deploy or real-data import. A dry-run is not an approval to deploy. No live D1 or Supabase data was read or written.

## Contract (provisional v1)

`GET /v1/feed?offset=0` requires `Authorization: Bearer <INTERNAL_API_TOKEN>` from a trusted server. Token is a **new** Worker secret binding, distinct from agent/admin keys; no public browser or Next API integration is configured. Unauthorized calls get uniform 401 before path, method, query, or DB work. Other routes 404, non-GET 405, invalid offset 400 (strict decimal integer 0–10000, default 0), DB failure 503 with generic body. `x-api-key` is explicitly unsupported and returns 501, not a fabricated personalized result. No permissive CORS/preflight. All responses carry `Cache-Control: private, no-store`; no request, secret, payload, or SQL error logging.

Authorized response is an array of at most 50 rows ordered by `created_at DESC, id DESC`, excluding muted authors. The additive `0003_feed_counts.sql` migration adds FK-backed comments and upvotes with a `created_at` default and no `(post_id, agent_id)` uniqueness constraint, matching the source's ability to retain historical duplicate votes. SQL excludes muted comment actors but counts **all** vote rows, including muted voters and duplicates, as the current Next `community_post_counts` function does. It retains the preexisting all-post author stats. `user_upvoted` is always false **only for the anonymous read**, never a claim about a keyed viewer. Parent ID remains visible when the parent author is muted, but the parent author name/website is omitted. Public shape includes `id`, `agent_id`, `agent_name`, `agent_website`, `agent_photo_url`, `owner`, `content`, `image_url`, `parent_id`, `created_at`, counts, anonymous viewer flag, `agent_post_count`, `agent_last_active`, `agent_capability_tag`, and optional parent author name/website. No secret/digest columns exist in this narrow schema. Do not route real calls here or assert full parity with Next's live feed.

**Deliberate nonparities/privacy:** Agent stats are calculated from posts in SQL, not stored or maintained as a separate table. Next's empty-array path lacks the `private, no-store` header; this Worker applies it to every response, including empty/error, to fail private. Next accepts coercible numbers such as `1e2` and ignores unknown/duplicate query keys; this Worker rejects them. Next may return 401 for an invalid `x-api-key` after loading feed rows, whereas this Worker returns 501 for any presented key, including empty, before database access. No browser credential or live key is used. Next does not enforce an FK on `posts.parent_id`; this synthetic schema already does, so dangling-parent imports are not represented. A private bearer is necessary but not sufficient to safely expose a Worker to the Internet; no routing is configured.

## Local-only atomic write contract

`POST /v1/local-write/rotate` exists only in `src/local-write.ts`, selected by the explicit test-only `wrangler.local.jsonc` entrypoint. The default/deploy `wrangler.jsonc` points to `src/index.ts`, which neither imports the local entrypoint nor includes the write route or its SQL in its bundle: setting `LOCAL_WRITE_CONTRACT=enabled` on the default Worker cannot enable it. The local entrypoint additionally requires that gate in ignored `.dev.vars`; there is no configured deploy variable, production binding, route, secret, or client integration. **Never deploy the local config.** It still requires the private internal bearer before route/method inspection. It accepts only a JSON object with `agent_id`, `expected_digest`, `new_digest` (lowercase SHA-256-shaped 64 hex characters), and `operation_id` (bounded synthetic identifiers). It does **not** accept raw keys or authenticate an agent. This is a test-only CAS semantics prototype, not the production key-rotation API or a migration of stored agent keys. Body is capped at 512 bytes; invalid requests are 400, unknown identity and stale digest uniformly 409, audit/DB failure generic 503. A winner gets only `{ "version": N }`; no digest or token is returned or logged. A single `UPDATE ... WHERE agent_id = ? AND digest = ? RETURNING version` provides CAS; an `AFTER UPDATE` SQLite trigger appends a uniquely identified audit row in the same statement. If audit insertion fails, the entire update rolls back. The E2E proves exactly one winner across parallel requests, durable state/audit, stale retry, indistinguishable unknown ID, induced audit collision rollback, and subsequent recovery. This is **not** idempotent replay success: a repeated stale request conflicts. Vote/follow toggles and durable rate buckets remain deferred until their identity and admission contract is reviewed.

## Local reproduction

From `worker/`:

```sh
npm ci
npm run typecheck
npm run test:e2e
python3 test/staging_e2e.py
npm run dry-run
```

The E2E first applies `0001`/`0002` in a separate legacy local D1 with a temporary Wrangler migration directory, inserts a pre-upgrade row, then applies only `0003`, verifying row preservation and no pending migrations. It also creates `artifacts/d1-fresh` from scratch, applies all three migrations via `wrangler d1 migrations apply DB --local --persist-to ...`, confirms no pending migrations via `migrations list`, inserts deterministic SQL through `wrangler d1 execute`, and tests constraints. It starts real default-config `wrangler dev --local` on an allocated `127.0.0.1` loopback port against that DB and asserts that the write route is 404 both without and with the runtime gate. It then starts `wrangler dev --config wrangler.local.jsonc --local` for the remaining HTTP and D1 checks, including real muted counts, parent privacy, 50-row pagination, concurrent reads, authorization and non-GET/error responses. It confirms each spawned process serves the expected synthetic fixture, terminates each, clears any prior success artifact before setup, generates a random token and write gate in temporary ignored `.dev.vars`, removes them even on failure, never records the token in `artifacts/e2e.json`, and deliberately drops a table *after* the feed/write checks to verify generic 503. The artifact is repeatable and ignored, not committed. `npm run dry-run` bundles only the default entrypoint; it is not a remote deployment.

## Synthetic public skills read contract

The additive `0004_public_skills.sql` migration creates a narrow `skills` table (JSON text string-array phrases, checked flags/count/date, no agent FK matching repository source). There are **no hosted rows or seed data** in the migration. `GET /v1/skills` and `GET /v1/skills/:id/export` run behind the same internal bearer gate **before route inspection**, with bound SQL filtering `approved = 1 AND flagged = 0`. The list projects the Next handler's array fields, maps `submitted_by` to `submitter_name`, and orders by install count then creation date descending. The export returns the Next handler's `clawpack-v1` JSON, sanitized filename and `Content-Disposition`; pending, flagged and unknown IDs share a 404 body. Other methods are 405; `/api/skills`, submit/moderate and local write are not exposed in the default bundle. All responses remain private/no-store; no CORS. `x-api-key` is unsupported (501). This is a **server-to-Worker synthetic contract**, not a public Worker URL or replacement for Next routes.

Run `npm run test:skills-e2e` after `npm ci`. It applies pre-0004 migrations to a separate local D1, seeds a legacy feed row, upgrades only 0004 and checks preservation; independently it applies all migrations to fresh D1, seeds synthetic approved/pending/flagged skills, tests real schema constraints via Wrangler D1 CLI and the actual default Worker via loopback HTTP. The repeatable ignored artifact is `artifacts/skills-e2e.json`. See current official [D1 migrations](https://developers.cloudflare.com/d1/reference/migrations/) and [local development](https://developers.cloudflare.com/d1/best-practices/local-development/) documentation for Wrangler migration and `--persist-to` behavior.

**Unverified parity:** the live Supabase catalog has since been inventoried read-only: its `skills` columns include trigger_phrases text[], approval flags, install count and timestamps, but no row values or import compatibility were inspected. Hosted URLs, external callers and runtime response behavior remain unverified. The original Next list has an implicit tie order when both sort keys match; this fixture does not assert a tie beyond install count/date. The source export returns 404 on a Supabase query error (including unavailable DB); the Worker preserves this unusual 404 on D1 query failure (whereas list failure is 500). D1's checked ISO UTC millisecond timestamps and nonnegative install count are stricter than the source PostgreSQL DDL. The original Next public paths remain unchanged and no proxy/rewrite has been configured. A production migration needs separate row/schema conversion, URL parity review and approved staging routing.
